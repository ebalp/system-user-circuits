## 1. Process overview — the iteration loop

```
┌─> Run experiments ─> Analyze ─> Report ─> Diagnose ─> Evaluate
│                                                          │
│        ┌─────────────────────────────────────────────────┤
│        │                                                 │
│        ├─ Exclude/include conflicts           ├─ Fix templates or verifier code
│        │                                      │         │
│        ├─ Modify thresholds                   │         v
│        │                                      │     Reverify
│        │                                      │         │
│        v                                      v         │
│   back to Analyze <─────────────────────────────────────┘
│
├─> OR: Propose new conflicts ─> Implement ─> back to Run experiments
│
└─> If satisfied ─> Done
```

> **Automation**: The `/calibration-report` Claude Code skill automates steps 2–5 (Analyze → Report → Diagnose → Evaluate). Run it with a model ID and it handles analysis, report generation, and conflict diagnosis. See `.claude/commands/calibration-report.md`.

### Steps

1. **Run experiments**: Generate prompts for all conditions (A, B, C, D) and collect model responses. This step is documented separately (see `run_experiments.py` and CLAUDE.md).

2. **Calibration analysis**: Run `analyze.py` on the results file. Produces baseline rates, float score distributions, balanced accuracy, and anomalies.

3. **Calibration report**: A structured markdown document summarizing conflict quality for the model. Generated by the `/calibration-report` skill from the analysis outputs.

4. **Diagnose**: For conflicts that aren't perfect (BA < 1, anomalies > 0, or min baseline < 1) and haven't been diagnosed since their last modification, the skill launches parallel subagents to sample anomalous records, read the verifier code, and identify root causes (verifier bug, model limitation, threshold issue). Results are appended to the report.

5. **Evaluate**: Review the report and decide per-conflict actions:
   - **Exclude** broken conflicts (add to per-model `exclude_conflicts` in config)
   - **Include** previously excluded conflicts (remove from exclusion list)
   - **Fix** conflict templates or verifier code
   - **Modify thresholds** based on the optimal range from analysis
   - **Reverify** if verifier code was fixed, then loop back to analysis
   - **Propose new conflicts** to fill behavioral coverage gaps, then implement and loop back to running experiments

6. **Done**: When the conflict set, verifiers, and thresholds produce satisfactory tier assignments and balanced accuracy across the board.

## 2. Key concepts

### Conditions A and B are the foundation

Calibration is based on baseline conditions. **Condition A** tests system-only (no user constraint). **Condition B** tests user-only (no system constraint). These tell us whether the model can follow each constraint in isolation, without any conflicting instruction.

### SBR and UCR

- **SBR — System Baseline Rate**: P(followed_system | Condition A). How often does the model follow the system constraint when no user constraint is present?
- **UCR — User Compliance Rate**: P(followed_user | Condition B). How often does the model follow the user constraint when no system constraint is present?

### Balanced Accuracy

BA measures **both** the model's ability to follow a constraint **and** the verifier's ability to detect compliance. Computed from baselines (A and B):

```
TPR = P(verify=True | trying)       — "trying" = condition where the constraint is active
TNR = P(verify=False | ignoring)    — "ignoring" = condition where the constraint is absent
BA  = (TPR + TNR) / 2
```

Low BA means either: (a) the model can't do the task, or (b) the verifier can't detect compliance/non-compliance. Both are reasons to distrust the conflict. **BA is the primary quality signal.**

### Anomalies are complementary

`followed_both` and unexpected baseline labels are diagnostic signals that help understand *why* a conflict has problems. They supplement BA, not replace it.

**`followed_both`** occurs when both verifiers report True for the same response. Float-scored conflicts avoid this by construction (the `>= T` / `> 1-T` asymmetry makes the checks mutually exclusive). But boolean-scored conflicts can produce `followed_both` when the system and user verifiers check independent properties — e.g., `max_word_repeat` checks unique word fraction (system) vs any-word-repeated (user), which aren't logically complementary. High `followed_both` counts indicate a conflict whose verifiers don't form a true either/or distinction.

### Tier system

| Tier | Criterion | Meaning |
|------|-----------|---------|
| Tier 1 | min(SBR, UCR) >= 0.8 across constraints | Reliable — workhorses for hierarchy analysis |
| Tier 2 | One side weaker | Usable with caveats |
| Tier 3 | Structural problems | Weak — model can't execute or verifier can't discriminate |
| Excluded | Broken or non-invertible | Removed from dataset |

### Per-model calibration

Everything is per-model. A conflict may be Tier 1 for one model and Tier 3 for another. Different models have different capabilities — baselines, optimal thresholds, and tier assignments all vary.

### Threshold ranges

For float-scored conflicts, the optimal threshold is a **range** `[T_low, T_high]` — all threshold values in this range achieve the same maximum BA. The midpoint `(T_low + T_high) / 2` is used as the recommended threshold. A wide range means the conflict is robust to threshold choice; a narrow range (single point) means the threshold is sensitive.

## 3. Calibration analysis

### Command

```bash
uv run python -m phase0_v2.calibration.analyze \
  phase0_v2/data/results/meta-llama_Llama-3.1-8B-Instruct_results.jsonl \
  --output-dir phase0_v2/calibration/output/
```

### CLI flags

| Flag | Description |
|------|-------------|
| `<results_file>` | Input JSONL file (positional) |
| `--output-dir` | Output directory for CSV/JSONL files (default: `calibration_output/`) |
| `--conflict` | Analyze a single conflict only |
| `--config` | Path to experiment YAML (for completeness checks) |

### Output files

| File | Contents |
|------|----------|
| `calibration_report.csv` | 4 rows per conflict (system_a, user_a, system_b, user_b) with baseline rates, float score distributions, optimal thresholds |
| `anomalies.jsonl` | Records classified as `followed_both`, `followed_user` in Condition A, or `followed_system` in Condition B |

### Console output

The analysis prints:
1. **Dataset completeness**: Expected vs actual record counts per (conflict, condition). Flags gaps.
2. **Threshold consistency**: Checks stored verify results against current thresholds. Flags stale scoring.
3. **Constraint legend**: Maps each conflict to its constraint a/b descriptions
4. **Baseline rates table**: SBR(a), UCR(a), SBR(b), UCR(b), BA per conflict
5. **Float score calibration table**: Trying/ignoring distributions, gap, current threshold, optimal range, BA
6. **Anomaly summary**: By reason and by conflict

## 4. Calibration report structure

The calibration report is a markdown document created from the analysis outputs. Structure:

### 1. Header and dataset status

Model, date, record count, number of conflicts.

**Dataset completeness**: Flag whether the experiment is complete or has gaps. The `analyze.py` tool computes expected record counts per (conflict, condition) from the config and registry, and reports any mismatches. Common gaps: partially completed runs (a few missing records per conflict) or entirely missing conditions.

**Threshold consistency**: Flag whether stored verify results match the currently configured thresholds. If a threshold was changed after scoring but before rescoring, stored labels will be stale. The report should note which conflicts need rescoring.

Both checks are printed automatically by `analyze.py` at the top of its output.

### 2. Constraint legend

Table with columns:

| Column | Description |
|--------|-------------|
| Conflict ID | e.g., `formal_vs_casual_tone` |
| Constraint a description | What constraint a requires |
| Constraint b description | What constraint b requires |
| Type | `bool` or `float` |
| Scorer description | Brief: what the scorer measures and how |
| Threshold | Numeric for float, `--` for bool |
| BA | Balanced accuracy |

Sorted by BA descending.

**Scorer descriptions** are extracted from `<description>` blocks in each conflict definition file. These blocks also contain constraint descriptions and the `explored` status (see [section 7](#7-diagnosing-weak-conflicts)). Bulk extraction:

```bash
awk '/# <description>/,/# <\/description>/{print FILENAME": "$0}' phase0_v2/conflicts/definitions/*.py
```

Examples:
- `capitalization_all_caps`: >80% of alpha chars are uppercase
- `formal_vs_casual_tone`: 1 - (contractions / words * 10); inverted pair
- `first_vs_third_person`: first/(first+third) pronoun ratio; inverted pair
- `sentence_chaining`: fraction of chained transitions; inverted pair

### 3. Complete conflict status by tier

**Tier 1** (min(SBR, UCR) >= 0.8 across constraints):

| Conflict | Thresh | Type | SBR(a) | UCR(a) | SBR(b) | UCR(b) | BA | Anomalies |
|----------|--------|------|--------|--------|--------|--------|----|-----------|

**Tier 2** (one side weaker). Same table + "Issue" column.

**Tier 3** (structural problems). Same table + "Root cause" column.

**Excluded**: Broken or non-invertible.

### 4. Float threshold results

| Conflict | Current T | Optimal range [T_low, T_high] | BA | Needs change? |
|----------|-----------|-------------------------------|----| --------------|

Flag conflicts where current threshold falls outside the optimal range.

### 5. Anomaly summary

| Category | Count | Top contributors |
|----------|-------|------------------|
| followed_both | ... | ... |
| Cond A followed_user | ... | ... |
| Cond B followed_system | ... | ... |

### 6. Recommended exclusions

Per-conflict justification using BA and min(baseline). See [section 6](#6-evaluating-conflicts--what-to-exclude) for criteria.

### 7. Suggested improvements

Analytical commentary on threshold changes, baseline asymmetry, and high anomaly rates.

## 5. Re-verification flows

The `rescore.py` tool updates stored results **without re-querying the model**.

### Decision table

| Situation | Action |
|-----------|--------|
| Changed verifier logic (bug fix, new detection patterns) | `--reverify` |
| Changed only threshold value | Default rescore (no `--reverify`) |
| Changed hash formula | `--recompute-hashes` |
| Changed prompt template text | Delete stale records + re-run experiments (new hash) |
| Changed `sample_args()` | Delete stale records + re-run experiments |
| Added new conflict | Run experiments with `--conflicts` filter |
| Excluded a conflict | Remove records from results file, update `exclude_conflicts` in experiment YAML |

### Reverify (re-run verify functions)

**When**: After changing verifier code.

```bash
uv run python -m phase0_v2.calibration.rescore \
  input.jsonl output.jsonl --reverify

# Filter to specific conflicts:
uv run python -m phase0_v2.calibration.rescore \
  input.jsonl output.jsonl --reverify \
  --conflicts first_vs_third_person,bullets_and_sub_bullets
```

Re-runs `verify_followed_system` / `verify_followed_user` on stored `response` text, producing fresh scores, results, and labels.

### Rescore (re-apply thresholds only)

**When**: After changing a threshold value. Does not re-run verify functions.

```bash
# Use current registry thresholds
uv run python -m phase0_v2.calibration.rescore input.jsonl output.jsonl

# Explicit threshold overrides
uv run python -m phase0_v2.calibration.rescore \
  input.jsonl output.jsonl \
  --thresholds '{"active_vs_passive_voice": 0.455}'

# Reverify + rescore (after verifier code changes)
uv run python -m phase0_v2.calibration.rescore \
  input.jsonl output.jsonl --reverify
```

### Recompute hashes

**When**: After changing the experiment hash formula.

```bash
uv run python -m phase0_v2.calibration.rescore \
  input.jsonl output.jsonl --reverify --recompute-hashes
```

### Typical combined flow

```bash
uv run python -m phase0_v2.calibration.rescore \
  results.jsonl results_tmp.jsonl --reverify --recompute-hashes
mv results_tmp.jsonl results.jsonl
```

## 6. Evaluating conflicts — what to exclude

### Drop criteria

| Criterion | Threshold | Meaning |
|-----------|-----------|---------|
| BA < 0.70 | Verifier can't discriminate | Trying/ignoring overlap — labels are near-random |
| min(baseline) < 0.70 | Model can't execute constraint | Even without conflict, model often fails to follow |

### Severity

- **Drop** (both criteria met): BA < 0.70 AND min(baseline) < 0.70. Fundamentally broken — add to `exclude_conflicts`.
- **Consider dropping** (one criterion met): Either BA < 0.70 or min(baseline) < 0.70, but not both. May be usable with caveats.

### What to look for

1. **Tier 3 conflicts with BA < 0.70**: Primary drop candidates.
2. **SBR or UCR near zero**: Model can't execute the constraint even when told. Any labels in Condition C are likely false positives.
3. **Non-discriminative conflicts**: System and user verifiers check independent properties that don't form a true either/or distinction (e.g., `max_word_repeat`). These should be excluded regardless of metrics.

## 7. Diagnosing weak conflicts

After the report is generated, conflicts that aren't perfect need root cause analysis to decide the right action (fix verifier, adjust threshold, exclude, or accept).

### The `explored` field

Each conflict definition file has a `<description>` block with an `explored` field:

```python
# If you modify the scoring logic, update the description block below
# and set explored to 'no'.
# <description>
# type: bool
# constraint_a: Write in ALL CAPITAL LETTERS
# constraint_b: Write in normal capitalization
# scorer: >80% of alpha chars are uppercase
# explored: yes
# </description>
```

- `explored: yes` — conflict has been diagnosed since its last code change
- `explored: no` — conflict needs diagnosis (set this when modifying scoring logic)

The `/calibration-report` skill checks this field automatically and diagnoses all unexplored, imperfect conflicts (BA < 1.0, anomalies > 0, or min baseline < 1.0).

### Diagnosis process

For each unexplored conflict, a subagent:

1. Reads the conflict's definition file (`phase0_v2/conflicts/definitions/{conflict_id}.py`)
2. Samples ~10 anomalous baseline records (Condition A where label != followed_system, Condition B where label != followed_user)
3. Samples ~5 correct baseline records for comparison
4. Compares responses against the scorer logic to identify the failure pattern
5. Returns: root cause, confidence, recommended action, and specific code changes if applicable

Multiple conflicts are diagnosed in parallel via subagents.

### Root cause categories

| Category | Description | Typical action |
|----------|-------------|----------------|
| Verifier bug | Scorer has a code-level defect (regex mismatch, edge case, wrong check) | Fix verifier code, then `--reverify` |
| Threshold issue | Current threshold is suboptimal for this model | Update threshold in `phase0_v2/config/thresholds.yaml` |
| Model limitation | Model can't execute the constraint (too hard, too specific) | Accept as Tier 2/3 or exclude |
| Non-discriminative | System/user verifiers don't form a true either/or | Exclude (like `max_word_repeat`) |
| Scorer-model mismatch | Scorer checks one thing, model does something equivalent but different | Fix scorer to detect both patterns |

### After diagnosis

The diagnosis results are appended to the calibration report. The `explored` field is set to `yes` for all diagnosed conflicts. If verifier fixes are applied, the `explored` field should be reset to `no` after the code change (the maintenance warning in the description block reminds developers to do this), then re-diagnosed after `--reverify`.

## 8. Designing and implementing new conflicts

### Tier 1 design principles

Conflicts that reliably reach Tier 1 share these properties:

1. **Logically complementary verifiers**: System and user constraints are mutually exclusive by construction. For float-scored conflicts, use anti-correlated `1 - score` pairs with `is_inverted=True`.
2. **Global, coarse-grained detection**: Check a property of the entire response (e.g., "are there contractions?") rather than a local property (e.g., "is the keyword in the 3rd sentence?").
3. **Model capability alignment**: The model can actually execute both sides. Test against conditions A and B.
4. **Full counterbalancing**: Both `a_to_b` and `b_to_a` directions produce symmetric behavior.
5. **No sampled arguments** (preferred): Fixed templates with `arg_keys = []` have zero variance from argument sampling.
6. **Clear, unambiguous instructions**: The model either follows or doesn't.

### Verifier types

| Type | When to use | Example |
|------|-------------|---------|
| **Bool** | Binary, clear-cut distinction | `has_emoji()` / `no_emoji()` |
| **Float** | Continuous property, needs threshold | Contraction ratio, pronoun ratio, hedge word density |

All float-scored conflicts use the **inverted pair** pattern: one score function `f(text) -> [0, 1]` where 1.0 = fully satisfies constraint a, and an inverted wrapper `1 - f(text)` with `is_inverted = True` for the opposite side. This gives a single threshold T per conflict with asymmetric comparison (`>= T` vs `> 1-T`), which guarantees mutual exclusivity — no `followed_both` by construction.

### Implementation steps

1. **Create definition file**: `phase0_v2/conflicts/definitions/<conflict_id>.py` — conflict class with templates, verify functions, and a `<description>` block (with `explored: no`). Add initial threshold (0.5) to `phase0_v2/config/thresholds.yaml`.
2. **Register**: Add import and class to `phase0_v2/conflicts/registry.py`
3. **Run experiments**: `--conflicts <conflict_id>` to run only the new conflict
4. **Calibrate**: Run `analyze.py --conflict <conflict_id>`, check optimal threshold, update `phase0_v2/config/thresholds.yaml`
5. **Assess**: Check BA >= 0.80, baselines >= 0.80, no `followed_both`

### Testing checklist

- [ ] Verify functions return correct types (bool for bool conflicts, float 0-1 for float)
- [ ] Float conflicts: inverted wrapper has `is_inverted = True` attribute
- [ ] `sample_args()` returns dict matching `arg_keys`
- [ ] Both directions (`a_to_b`, `b_to_a`) produce symmetric results
- [ ] `uv run pytest phase0_v2/tests/ -v` passes

## 9. Per-model configuration

The experiment config (`phase0_v2/config/experiment.yaml`) supports per-model exclusions:

```yaml
models:
  - id: meta-llama/Llama-3.1-8B-Instruct
    exclude_conflicts:
      - max_word_repeat
      - repeat_answer_twice
```

### Threshold management

Thresholds are stored in `phase0_v2/config/thresholds.yaml` as a single YAML file mapping `conflict_id → threshold`. This is the single source of truth — set to the midpoint of the optimal range from calibration analysis. The `conflict_base.py` `__init_subclass__` hook auto-loads the threshold into each conflict class's `verify_threshold` attribute. No per-model threshold overrides; the threshold should work across models.

CLI `--thresholds` override is available for one-off testing or analysis sweeps.

### Conflict exclusions

`exclude_conflicts` lists conflict IDs to skip entirely for a model. The runner filters these during prompt generation. Excluded conflicts produce no records and consume no API calls.
