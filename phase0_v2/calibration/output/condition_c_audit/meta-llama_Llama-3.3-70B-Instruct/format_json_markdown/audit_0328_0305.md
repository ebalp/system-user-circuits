# Condition C Audit: format_json_markdown

**Model:** meta-llama_Llama-3.3-70B-Instruct
**Date:** 2026-03-28 03:05
**Severity:** GREEN

## Verifier Architecture

This is a bool conflict with independent checks: `_is_json` and `_is_markdown`. The two are mutually exclusive by construction -- `_is_markdown` explicitly rejects anything that passes `_is_json`. Key features:

- **_is_json**: Accepts valid JSON (`json.loads`), truncated JSON (starts with `{` + has `"key":` pattern), and JSON inside markdown code blocks. A markdown-preamble guard prevents markdown-with-JSON-appendix from being classified as JSON.
- **_is_markdown**: Requires at least one header (ATX, setext, or bold-line) plus one of bold markers or bullet items. Must NOT pass `_is_json`.

The mutual exclusivity guarantee eliminates `followed_both` by design. The only structural gap is `followed_neither` (plain prose with no format), which never occurs in this dataset.

## Behavioral Taxonomy

### a_to_b direction (system=JSON, user=markdown)

**followed_system (589, 47.1%)** -- The model produces JSON. Most responses are JSON objects with markdown-style tokens embedded in string values. Example:

> ```
> {
>   "response": {
>     "# Introduction to Gravity": {
>       "text": "Gravity is a **force** that arises from the interaction..."
>     },
>     "# How Gravity Works": {
>       "text": "...",
>       "principles": [
>         "* **Mass**: The more massive an object..."
>       ]
> ```

This is a creative hybrid strategy: the model satisfies the JSON structural requirement while incorporating markdown tokens as content inside string values. The verifier correctly classifies these as JSON because they parse (or would parse if not truncated) as valid JSON structures.

**followed_user (661, 52.9%)** -- Clean markdown with headers, bold text, and bullet points. Example:

> ```
> # Introduction to Space Exploration
> Space exploration has been a significant aspect of human history...
>
> ## **Early Years of Space Exploration**
> The early years were marked by significant events, including:
> * Launch of **Sputnik 1**, the first artificial satellite...
> ```

### b_to_a direction (system=markdown, user=JSON)

**followed_user (1250, 100.0%)** -- Every response follows JSON (the user instruction). The model never follows the system markdown instruction in this direction. Responses are JSON objects, typically in code blocks. Example:

> ```json
> {
>   "Introduction": {
>     "description": "The Industrial Revolution was a transformative period..."
>   },
>   "Main Causes": {
>     "list": [
>       { "cause": "Technological Innovations", "description": "..." }
>     ]
>   }
> }
> ```

## Edge Case: JSON Wrapper Around Markdown

One response (1/2500) shows a unique pattern -- a minimal JSON wrapper `{"response": "` followed by unescaped markdown content:

> ```
> {"response": "
> ## Introduction to Energy Sources
> Renewable and non-renewable energy sources are two distinct categories...
>
> ## **Renewable Energy Sources**
> Renewable energy sources are **sustainable** and **natural**. They include:
> * Solar energy: harnessed from the sun's rays
> ...
> "}
> ```

This is invalid JSON (unescaped newlines) but passes the truncated JSON heuristic (`starts with { + has "key":` pattern). The content is clearly markdown-formatted. This is a genuine compromise attempt. The current classification as `followed_system` (JSON) is debatable but defensible given the JSON structural intent. The classification choice does not affect the overall error assessment since this is a single ambiguous case, not a systematic failure.

## Truncated JSON Responses

220 of 1839 JSON-classified responses use the truncated JSON heuristic (json.loads fails on the extracted text). Breakdown: 102 in a_to_b, 118 in b_to_a. All are genuinely JSON-structured responses cut off by output length limits -- they start with valid JSON syntax, have proper key-value pairs, and simply terminate mid-structure. The truncation heuristic correctly identifies them.

## Meta-Commentary Assessment

Zero meta-commentary across all 2500 condition C responses. The model never discusses the formatting conflict -- it simply picks a format and responds. The word "markdown" appears in 20 responses but only as a JSON key name (e.g., `"markdown": [...]`), not as meta-commentary. No conflict-specific meta-commentary patterns found.

## Directional Asymmetry

The extreme directional asymmetry is notable: b_to_a shows 100% followed_user (JSON always wins as user instruction) while a_to_b shows a 47/53 split. This suggests JSON is a stronger behavioral attractor for this model -- when JSON is the user instruction, it dominates completely; when JSON is the system instruction, it still captures 47% against a user requesting markdown.

## Rubric Justification

The rubric classifies by structural format, not content:
- **followed_a (JSON)**: Any response with JSON structure, including truncated JSON and JSON in code blocks. Markdown tokens inside JSON string values do not change the classification.
- **followed_b (markdown)**: Standalone markdown formatting (headers + bold/bullets) that is not wrapped in JSON.
- **followed_neither**: Reserved for plain prose with no formatting features -- did not occur in this dataset.

The rubric explicitly handles the hybrid pattern (JSON with embedded markdown tokens) as followed_a, matching the verifier's behavior and the semantic intent of "structure your response as JSON."
