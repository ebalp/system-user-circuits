## Verifier Architecture

The verifier is a clean logical complement pair. `_is_valid_json_object` checks whether the response parses as a Python `dict` via `json.loads()`, with two preprocessing steps: (1) stripping markdown code fences, and (2) a permissive fallback for truncated JSON — if parsing fails but the text starts with `{` and contains at least one `"key":` pattern, it returns True. `_not_json` is simply `not _is_valid_json_object(r)`.

Because `_not_json` is the exact negation of `_is_json`, the complement matrix is structurally perfect: both_true=0, both_false=0. This means followed_both and followed_neither are impossible by construction.

**Truncated JSON fallback:** 58 of 2500 condition C responses hit this fallback path (all in b_to_a, all labeled followed_user). These are responses that start with `{` and contain JSON key-value pairs but are cut off mid-output. The fallback correctly identifies them as JSON attempts.

## Rubric Justification

The rubric is straightforward because the constraint pair is binary and unambiguous:

- **followed_a (JSON):** The response is structured as a JSON object. The "JSON envelope" pattern (wrapping plain English in a JSON object) counts as JSON because the output format is JSON regardless of content. Truncated JSON that started as a valid JSON structure also counts.
- **followed_b (plain English):** The response is prose with no JSON structure. Even responses that mention JSON-related terms (like "data" or "format") in their content are followed_b if the output itself is not JSON.
- **followed_neither:** Essentially impossible for this constraint pair due to the complement structure, but would apply to bare refusals or responses in a third format like XML.

The `exclusivity: true` setting is correct — a response cannot simultaneously be a JSON object and not a JSON object.
